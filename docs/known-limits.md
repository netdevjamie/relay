# Known limits and flaws

What is wrong with Relay today, or not built, that someone using it should know. Each entry says what happens, what it costs you, and its status.

Rule: when a change ships with something known wrong, unfinished or unchecked, it is added here in the same change. When a flaw is fixed, its entry is removed in the change that fixes it. This file is the list; a handoff or a chat is not.

## Routing and gates

| Flaw | What it costs | Status |
| --- | --- | --- |
| The owner's notes reach an agent only when it is dispatched. An agent that is already running never sees a note left afterwards (`relay note` says so). Notes are plain text: nothing checks that a later role honoured one, and a note cannot be retired or limited to one phase (a later note that says otherwise is the only way; agents are told a later note stands over an earlier one and that no note waives a required check). One note is limited to 4,000 characters, but the number of notes is not, and every later agent is given all of them. | A note left mid-phase takes effect from the next phase. Whether it was followed is for the Reviewer and the owner to see. | Open |
| `relay override` to an earlier phase is recorded as an approval. | The ledger reads as if the owner accepted work they were in fact rejecting. Use `relay send-back` where it is offered. | Open |
| A phase that was started and then stopped leaves a step with no artifact, and there is no way to mark it withdrawn. | The history shows a step that never produced anything. | Open |
| The limit (`max_retries`) counts only rounds nobody chose. Rounds the owner chose are counted by the tripwire instead: a Reviewer's, Tester's or Security's high after 2 fix rounds of any kind stops for the owner, with a count of the fix rounds, and again after every later round that holds one (`FIX_ROUNDS_BEFORE_THE_OWNER_DECIDES` in `orchestrator/routing.py`). Relay does not stop when a round fails to close what it was sent to fix, or when a closed finding comes back, while no report holds a high. Confirmed by: `test_replay_one_automatic_round_then_four_gate_send_backs_never_reaches_limit_3` and the class `TestTheFixRoundTripwire` (`orchestrator/tests/test_automatic_rounds.py`). | Before 2 fix rounds the owner, or a session acting for the owner, can keep choosing rounds with `relay send-back` or `relay override` with no stop. A loop of mediums never trips it: each medium already stops at a gate. | By design |
| The tripwire counts every Builder step after the first as a fix round (`fix_rounds` in `orchestrator/run_state.py`), whatever ended it: a step that changed nothing, one that ended `needs-architect` or `blocked`, and an override into the Builder all count. Confirmed by: `test_fix_rounds_counts_every_builder_step_whatever_its_verdict` and `test_rounds_chosen_at_a_gate_or_by_override_or_note_count_the_same` (`orchestrator/tests/test_automatic_rounds.py`). | The stop can come before 2 rounds that fixed something. The owner sends the task on with one `relay send-back`. | Accepted limit |
| The tripwire's threshold is a constant (`FIX_ROUNDS_BEFORE_THE_OWNER_DECIDES` in `orchestrator/routing.py`), not a setting in `config.yaml`. The legacy `pentest` verdict `vulnerable` is outside it. When the retry limit stops the same route, the one stop is the limit's (`retry_limit`, the task `blocked`), with the count of fix rounds and a recommended send-back, where the limit alone recommends none. Confirmed by: `test_the_legacy_pentest_verdict_is_outside_the_tripwire`, `test_the_retry_limit_and_the_tripwire_on_one_route_make_one_stop_with_the_list` and `test_the_limit_alone_still_stops_as_before_and_lists_nothing` (`orchestrator/tests/test_automatic_rounds.py`). | Changing the threshold is a code change. A legacy Pentest high goes back to the Builder at any round. | Open |
| A send-back with no note sets the count of automatic rounds back to 0 like any other. `relay send-back` prints that no note was recorded and how to add one. | A session can reset the count without saying why. The ledger shows that it was sent back and when. | Accepted limit |
| A `blocked` task reads as stopped at the limit only when its latest verdict is one Relay routes back on its own and the count for that phase is at the limit. Otherwise it reads "Paused" and does not take a send-back: for one, a stopped task after `max_retries` has been raised. Ledgers written by older versions of Relay can hold more such tasks. An override on a task that reads "Paused" resets only the count of the phase it moves to. | These move by `relay override <task> <phase>` or `relay abort`. Nothing in the ledger but the latest verdict and the count tells a stopped task from a paused one. | Open |
| A Builder's fix report is named `-fix-N` by the number of Builder steps before it in the task. An override into the Builder, and a Builder run after its own `needs-architect`, are therefore named `-fix-N` too. Reviewer and Tester reports take `-pass-N` from their own count of automatic rounds, which is almost always 0. | A file name says how many times the Builder ran, not why. The step number in front keeps names unique. | Accepted limit |
| `relay send-back` saves the new step before it writes its `sent_back` event. If Relay dies between the two, the new step is in the ledger and waits on its agent, which that run never started, but the count is not reset and the send-back is not in the ledger. Until the next save, the task folder's `run.yaml` (a copy of the ledger, never read back) also still shows the count from before the send-back. | After such a crash the task may stop at the limit a round early; `relay send-back` or `relay override` clears it. `relay status` reads the ledger and is right. | Open |
| Accepting Security findings and closing a task after a deploy both use `relay override <task> done` at the terminal. On the phone's card (`relay card`) they are two choices with their own names and words: `accept-close`, "Accept the findings and close the task. Nothing is deployed.", and `deploy-done`, "Close the task: you have deployed it and the smoke test passed." No card offers both, and its `move-to` leaves out `done` beside either. Confirmed by: `test_look_alike_choices_read_differently` and `test_every_gate_kind_has_its_choices` in `orchestrator/tests/test_gate_card.py`. | Typed at the terminal, only the gate kind tells the two apart. On the card the words do. | Open |
| Security's verdict is capped at `findings` whenever the repo's profile lists no `security_test_targets`, even for a documents-only task with nothing to attack. | Such a task always ends at an owner gate that recommends sending the work back, with no finding behind it. | Open |
| The prompt Relay prints for an agent carries only the task, the paths, the recorded test run, the owner's notes and, for the Reviewer, Tester and Security, one sentence naming the three ratings. Confirmed by: `test_rating_phase_is_told_the_three_ratings` and `test_other_phases_are_told_nothing_about_ratings` (`orchestrator/tests/test_phase_prompt.py`), which read what `agents.build_prompt` returns. | Whoever dispatches the agent still has to add by hand what kind of pass it is (a re-review, a re-test) and which commits changed. A dispatch without that context would repeat work or miss the owner's override of the brief. | Open |
| The files backend (`persistence_backend: files`, the value when `config.yaml` names none; the example config an install copies sets `sqlite`) records no events: no approvals, send-backs, owner notes or test runs. | A task on that backend has no audit trail, no notes and no recorded test evidence. Set `persistence_backend: sqlite` in `config.yaml` for the ledger. | Accepted limit; the files backend is kept for older installs |
| A task on the files backend has no events to recount, so a stored count of automatic rounds is kept as it is, including one counted under an older rule that also counted send-backs. | Such a task may stop at the limit one or more rounds early and ask. One `relay send-back` clears it. | Accepted limit |

## Ratings and the threat model

| Flaw | What it costs | Status |
| --- | --- | --- |
| Ratings by consequence and by the threat model are judged by the roles, not by code: whether a high names its wrong behaviour, its attacker or the decision that goes wrong, whether a finding is inside the threat model, and whether an untrue statement would lead to a wrong decision. No code reads either. The rules are under "Threat model and ratings" in `agents/builder.md`, `reviewer.md`, `tester.md` and `security.md`. | A role that rates by category is not stopped. The Reviewer and the owner are the check. | By design |
| Every role reads the repo's `.relay/threat-model.md` as it is on the task's base branch by its instructions (`git show {base}:.relay/threat-model.md`). Relay's code does not read the file, and does not check that it exists, what shape it has, or that a role read the base's copy and not the branch's. Confirmed by: `grep -rn "threat-model" orchestrator --include=*.py --exclude-dir=tests` finds no line; `test_every_role_reads_the_threat_model_at_the_base` (`test_agent_prompts.py`) holds the instruction. | A role that reads the branch's copy, or none, works to the wrong model unseen until the Reviewer, Security or the owner reads its report. Security names a branch's change to the file as a finding. | Not built |

## Test evidence

| Flaw | What it costs | Status |
| --- | --- | --- |
| Relay does not check that a manual test plan exists when one is needed, that it was run, or that its results were filled in and committed. The Tester's prompt asks for the plan; nothing enforces it. Filling in results needs a text editor, not a phone. The plan's folder is fixed at `docs/manual-tests/`; a profile cannot move it. After the owner runs a plan and it passes, the gate still reads as a warnings verdict that recommends sending back; the owner accepts with `relay override`. | A task can be accepted at the gate with an unrun plan. The owner has to open the plan and see the empty "Actual" column. | Open |
| A task can complete without a passing recorded run at its final commit. | The rule "no pass or merge without a recorded passing run at that commit" is stated but not enforced. Security and Ops changes after the Tester are not re-tested by Relay. | Not built |
| A drop in test count or new skipped tests is recorded but not flagged. | A Builder that deletes or skips tests is caught only if the Reviewer compares the counts. | Not built |
| Relay's recorded test run reports counts only. Nothing names the test files a round deleted, renamed or took a line out of. Confirmed by: the keys of a recorded run, listed in the docstring of `evidence.run_tests` (`orchestrator/evidence.py`), include `counts` and no list of files. | A rewritten test keeps the count, and only the Builder's list of existing tests changed or removed, and the Reviewer's own list from the diff, show it. | Open |
| Only the text of the test command is compared with the base branch. | A branch that keeps `npm test` but changes what it runs (a script, a Makefile, a test config) is not stopped for the owner. | Accepted limit; counts and the Reviewer cover it |
| Counts need a JUnit report named in the profile (`test_report`). | Repos that don't write one show "counts unknown". | By design |
| A test command that rewrites tracked files or leaves unignored files makes every run `uncommitted`. | The task bounces to the Builder until the retry limit stops it. `relay profile` warns only about the report file, not other leftovers. | Open |
| Relay does not prove that a fix's test fails before the fix. | The Reviewer and Tester are told to check it by hand. | Not built |
| While a Builder or Tester verdict is waiting, `gate-check` can read `ready` although `relay next` will run the tests first and may send the work back. | A front end may show "ready" for work that is about to bounce. | Documented in `docs/json-api.md` |
| A repo with no `.relay/profile.yaml` gets `not_run` for test evidence. | Relay records no test run for that repo's tasks. | By design; add a profile (`docs/profile.md`) |

## Running agents

| Flaw | What it costs | Status |
| --- | --- | --- |
| A closed lid, or a flat battery, still puts the Mac to sleep in the middle of a phase. Relay holds the Mac awake itself for up to two hours per phase (`keep_awake_seconds`) and, when `relay next` picks up a step's verdict, says and records how often and how long the machine slept between the step being dispatched and its artifact being written. It cannot prevent lid-closed sleep; a phase longer than the hold is unprotected for the rest; the hold starts at dispatch, so in manual mode it can run out before a late-started agent finishes; and the sleep check reads the system's power log, which keeps about a week and exists only on macOS, so an older or non-Mac step is "unknown". | Work can still stall for hours, though the stall is visible afterwards instead of silent. The real fix is running agents somewhere that does not sleep. | Open |
| Relay is driven from a phone only through the Claude Code session on the Mac that drives it, by Remote Control (README, "From your phone"), with `relay waiting`, `card`, `show` and `decide`. Editing a manual test plan, and heavy builds, still need the computer. Confirmed by: `orchestrator/tests/test_gate_card.py` and `orchestrator/tests/test_decide.py`; the round trip on a real phone is for the manual test plan `docs/manual-tests/relay-mobile-gates.md` to show. | Reading a gate through a chat session is slower than a page, and every word reaches Relay through that session (see the row on notes under "Reading a gate"). | Open |
| `relay decide` holds a lock per task (`locks/<task>.decide.lock` in Relay's home) while it reads the gate, checks the choice and applies it, so of two decides on one gate at the same moment one applies and the other is refused with nothing recorded. The deciding commands typed at the terminal (`override`, `send-back`, `abort`) take no lock, so one typed while a `decide` is being applied can still apply as well, as two of them typed together always could. Confirmed by: `test_a_second_decision_while_the_first_is_applied_is_refused` (`orchestrator/tests/test_decide.py`), and `_one_decision_at_a_time` is entered only from `cmd_decide` (`orchestrator/commands.py`). That a terminal command and a `decide` together both apply is reasoned from that code, not run. | A gate decided at the terminal and from the phone at the same moment can get two decisions and two agents. | Open; the fix is for the deciding commands to take the same lock |
| Nothing reaches the phone while the Mac sleeps: no push and no card, and the session reads as offline in the Claude app until the Mac wakes and Remote Control reconnects. Confirmed by: Claude Code's Remote Control documentation, not run; the lid-closed step of the manual test plan is to show it. | A gate reached with the lid closed waits until the Mac wakes. Keep the lid open on power while away; Relay holds the Mac awake up to two hours per phase (row above). | Open |
| Claude Code's own permission prompts are outside Relay: Relay cannot see, push or answer one. Claude Code pushes one to the phone only when Remote Control is on for that session and **Push when actions required** is on in `/config`; a prompt in auto mode (`claude --print`) cannot be answered from anywhere. Confirmed by: Claude Code's documentation, not run. | A role can wait for hours on a prompt nobody sees. Turn both settings on (README, "From your phone"). | Open |
| An approved deploy is not run by Relay. Ops prepares; the owner deploys by hand and closes the task. | Nothing checks that what was deployed is what was approved. | Not built |
| Nothing in a profile except `commands.test` is ever run by Relay. | Build, lint, audit and smoke commands are advice to the agents. | Not built |
| Under `--auto`, Relay runs `claude --agent <name>` with the name from `AGENT_NAMES` in `orchestrator/agents.py`. The map is held to the `name:` line of the repo's `agents/*.md`, not to the copies in `~/.claude/agents` that Claude Code reads (the copies row below). When `claude` exits non-zero, Relay stops with code 1 and prints that the role "did not start or did not finish", since the exit code cannot tell the two apart. The step stays recorded as dispatched with no report. For a pipeline phase the line names `relay override <task> <phase> --auto`, which starts it again; for any other phase the line names `relay status <task>`. The legacy `pentest` phase has no role file: under `--auto` Relay refuses it before anything runs; manual mode still prints `@pentest`. Confirmed by: `test_every_dispatchable_phase_has_a_role_file_with_its_name`, `test_auto_dispatch_passes_the_role_files_name`, `test_a_non_zero_exit_stops_relay_and_says_the_role_did_not_start`, `test_override_dispatches_a_stopped_phase_again` and `test_a_phase_with_no_role_file_is_refused_under_auto_before_claude_runs` (`orchestrator/tests/test_agent_dispatch.py`). These tests record the command instead of running `claude`. | A hand-edited `name:` in `~/.claude/agents` makes `--auto` fail with the stop line. | Accepted limit |
| A running Claude Code session may keep the role prompts it loaded when it started, and then installing a changed prompt does not change what agents dispatched from that session are told. Claude Code's documentation says a file edited in `~/.claude/agents` or `.claude/agents` is picked up by the next delegation with no restart, with three exceptions (a folder that did not exist when the session started, a folder added with `--add-dir`, a session started with `--disable-slash-commands`); old role text has nonetheless been seen in sessions started before an install. What a role does when its prompt and its role text disagree was not run. | Install when no Reviewer, Tester or Security is running, and dispatch from a new session after. `./setup.sh` changes the prompt Relay prints at once, so a role dispatched from an older session that still holds the old role text can be told two different things, and may follow the softer one. `DEPLOYMENT.md` says the same for whoever installs. | Open |
| The role prompts exist in several copies (repo, install folder, `~/.claude/agents`). A project-level `.claude/agents` folder at or above the folder a session starts in is one more: `./setup.sh` does not write it, and a file in it, or in a folder under it, whose frontmatter `name:` is that of a Relay role is loaded in place of that role in `~/.claude/agents`, whatever the file is called. Each repo, and each worktree of it, can hold its own `.claude/agents`, so a repo that tracks old role files gives them to every checkout. The two searches in `DEPLOYMENT.md` do not see everything: not a file that is a symlink or sits in a symlinked sub-folder, not a folder that is itself a symlink, not a name written another way YAML allows (`name : Builder`, a comment after the name, indented keys, the name on the next line, a folded scalar, a quoted key), and the second not a folder more than five levels down. No command is known that shows which file an installed role comes from. Confirmed by: Claude Code's subagent documentation ("When multiple subagents share the same name, Claude Code uses the one from the higher-priority location", with `.claude/agents/` above `~/.claude/agents/`; "identity comes only from the `name` frontmatter field"); `test_the_install_notes_search_finds_every_role_by_the_name_inside_the_file` and `test_the_search_over_every_project_folder_finds_every_role_in_each` (`orchestrator/tests/test_install_notes.py`) run the two searches on stand-in folders. | A prompt edited in the wrong place is overwritten by the next install. Edit `agents/` in the repo only. An install changes nothing for a role whose `name:` is in a file under a project-level folder until that file is moved away. Before and after an install, search for the names, not the file names (`DEPLOYMENT.md` has the two commands, what they miss, and the checks in order). | Open |
| The size of a role file is held by a test for four of the seven only (`builder.md`, `reviewer.md`, `tester.md`, `security.md`): no line outside a table or a code block is longer than 450 characters, and each file has a word ceiling. `architect.md`, `designer.md` and `ops.md` are held by neither, and three lines in them are over the limit (`architect.md` line 43; `designer.md` lines 43 and 56). The test counts characters and words, so it cannot tell a line that holds one rule from a line that holds three short ones. Confirmed by: `WORD_CEILINGS` and `ROLE_FILES_WITH_NO_SIZE_LIMIT` in `orchestrator/tests/test_agent_prompts.py`. | A change can pack rules into the three files that are not held, or three short ones into a line under the limit, and no test fails. Whoever reviews a role file still has to read it whole, as the role that follows it. | Open; holding the other three means splitting their lines first |
| Ops has no automated execute mode. At the deploy gate Relay prints the Ops report's steps for the owner to run, then `relay override <task> done` closes the task (`GATE_DEPLOY_APPROVAL` in `orchestrator/commands.py`). Nothing checks a deploy command against the owner's approval: `agents/ops.md` says the rule is kept by the prompt only. | An Ops role that ignored its prompt could run a deploy command in prepare mode; no hook or tool stops it. Read the Ops report before deploying. | Not built |
| Seen to fail runs a test in a clone, and a clone holds only committed files: nothing the project ignores (installed dependencies, local settings, build output). | On a project whose tests need ignored files, the role installs them in the clone or reports the test under Not verified. | Accepted limit |
| In Seen to fail, the line that lets a script hold the clone's path (the "A script" item in `agents/builder.md`, `reviewer.md` and `tester.md`) asks that the script check "that the path's resolved top-level folder is that folder"; the next step checks for an empty path. A script that keeps one variable for both the folder it made and the path it uses compares the path with itself, which only asks whether the path is the top of some checkout. If that script also skips the next step and resolves the path with a function that turns an empty string into the current folder (Python's `os.path.realpath`), then with an empty path, run from the top of the task's checkout, it breaks and runs its undo in the worktree. Confirmed by: runs on a stand-in repo, where such a script lost the uncommitted work there, and the same script with the empty-path step stopped. | A role that writes such a script loses the uncommitted work in the task's checkout, which Seen to fail exists to prevent. It takes a script that skips a numbered step of the procedure it is running. | Open; the fix is for "is that folder" to become "is the folder it made, kept apart from the path", in the three files, within their word ceilings |
| `agents/security.md` says: "When targets are listed but none reaches the change, a local copy this run made and will delete counts as one." For a change a listed target reaches in part (a route, say, and a function the route never calls) the line reads two ways. By the letter a target reaches "the change", so the line does not apply: the function may not be attacked in a throwaway copy, the stop for "A new input or output path that was not attacked" rates it medium, and the report is `findings` with nothing found. Read path by path, the copy counts for the function and it can be attacked. It is a reading, not a run: `test_a_throwaway_copy_is_a_safe_target_only_where_no_listed_target_reaches_the_change` holds the line's words and place, not which way a role reads it. | Neither reading allows anything unsafe. By the first, a task can end at an owner gate that recommends sending the work back with no finding behind it. | Open; the fix is "none reaches a new path" in place of "none reaches the change" |

## Reading a gate (`relay card`, `relay show`, `--json`)

| Flaw | What it costs | Status |
| --- | --- | --- |
| "Running" means the current step has no report with a verdict yet. Relay does not know whether an agent is alive. | A phase whose agent died, or was never started, reads as running since its dispatch time. | Open |
| Notes do not record who typed them. The ledger lists every note as the owner's, including ones a session wrote on their behalf. So does `relay decide`, which the session driving Relay runs for the owner from their phone: it records whatever note it is given as the owner's, and then prints it back under `Recorded:` as the ledger holds it, which is how the owner checks. Confirmed by: `test_decide_note_is_recorded_as_given` (`orchestrator/tests/test_decide.py`). | A session's paraphrase reads as the owner's own words, unless the owner reads the `Recorded:` block. | Open |
| Reports written by older role prompts have no rated findings. The card puts their findings under "Not rated", or says the findings are in the report. A row a role writes wrongly is listed under "Not rated" as written, never dropped. | No severity list for old work. Nothing rewrites an old report. | By design |
| A report over 1 MB is not shown; `relay card` and `relay show` name the file. A report whose bytes are not UTF-8 is shown with replacement marks. | A very large report has to be opened as a file. | Accepted limit |
| To find the verdict of a step that `relay next` has not recorded yet, the card and the `--json` commands read only the first 64 KB of its report. A report whose opening block (between the two `---` lines) does not end within 64 KB reads as having no verdict; `relay next` reads no opening block longer than 64 KB either. | Such a step shows as still running. A normal opening block is under 200 bytes. | Accepted limit |
| On some SQLite versions `relay status`, `list` and `gate-check` with `--json` cannot open the ledger read-only while the ledger's two side files (`relay.db-wal`, `relay.db-shm`) are absent, as they can be when no Relay command has it open. Seen with SQLite 3.51.0; 3.53.4 opens it. They report it as an internal error and do not fall back to a writable connection. | Such a read fails until a Relay command has the ledger open, or until it is run with a Python that has a newer SQLite. | Open |
| A report file that is not a regular file (a named pipe, a device) is refused before it is opened, by the card and by the `--json` commands. The check and the open are two steps, and `relay next` and the other commands that write still open a report without the check. | Someone who can already write in a task folder could still stall `relay next` with a named pipe, or win the gap between the check and the open. | Open |
| The card says a gate is clean ("No findings at this gate", "Security found nothing to fix") only when the verdict in the ledger agrees, or Security's own capped line says yes, and the whole file, quotes and code blocks included, holds exactly one line that begins with the words "rated findings", no row-like text the reader did not take, and no code fence left open. A report's headline and capped label are shown only when the words `Summary for the owner:` or `Capped verdict:` appear once in the whole file, under a title that is the report's first line. | A report that quotes any of these strings (a report about the card itself, for one) loses its own headline, or gets "The card may not have read every finding" under a list that is in fact whole. Rows quoted from the first column are listed as findings too. | Accepted limit |
| Two things the card cannot tell from a report's text. A report that leaves out its own summary line or capped line, and quotes one directly under its title (or has no title and begins with a quoted one), gets the quoted line as its headline or capped label. And under a verdict that means nothing was found (`approved`, `pass`, `secure`), a report whose findings are written as prose, with a quoted `## Rated findings` section saying `None.`, is shown as having none. Two more cases, under any verdict, when a role writes no rated section of its own (its findings are a list under `## Findings`, or a table under a heading the card does not read, such as `## Rated finding`) and quotes a whole section, outside a code block and from the first column. If the quoted section holds a valid row, the card lists the quoted row, and the role's real finding is not listed. If the quoted section says `None.` and Security's own capped line says yes, the card says "No findings at this gate" and "Security found nothing to fix" under the verdict `findings`. | Each needs the role to break its prompt and to quote these strings. The full report is always one `relay show` away. No check of the text can tell these from an honest report, which also has a `## Findings` section in prose. | Accepted limit |
| A Security report can be capped and still list a finding rated low: `agents/security.md` says to write `Capped verdict: yes` when the profile names no safe test target and nothing found is rated medium or high. The card then says "Security marked this verdict as capped but lists 1 finding. Read them.", which reads as if Security had made a mistake. Confirmed by: `CAPPED_BUT_LISTS` in `orchestrator/board_view.py`, which `_capped_sentence` returns whenever the card lists a finding; `agents/security.md`, "Attack it" and "Verdict". | The owner may take a correct capped report for a wrong one. The sentence still sends the owner to the rows, which is the right thing to do. | Open |
| Reading the ledger while no other Relay command has it open makes SQLite create its two empty side files (`relay.db-wal`, `relay.db-shm`) next to it, as `relay list --json` already does. The ledger file itself is not changed. | Two extra files may sit beside the ledger. | Accepted limit |
| The count of automatic rounds is not stored: each read of a task works it out from that task's `retry`, `sent_back` and `approval` events, and `relay list` reads every task. | A list grows with history. Measured on a scratch ledger (median of 5): 138 tasks at 1,000 events each took about 43 ms a list; at 3,000 events each, about 113 ms. | Accepted limit |
| An event whose payload cannot be read (not JSON, nested too deep, or JSON that is not an object) is not skipped by the one place that reads a task's events, `db.get_events`.
