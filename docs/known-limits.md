# Known limits and flaws

What is wrong with Relay today, or not built, that someone using it should know. Each entry says what happens, what it costs you, and its status.

Rule: when a change ships with something known wrong, unfinished or unchecked, it is added here in the same change. When a flaw is fixed, its entry is removed in the change that fixes it. This file is the list; a handoff or a chat is not.

## Routing and gates

| Flaw | What it costs | Status |
| --- | --- | --- |
| The owner's notes reach an agent only when it is dispatched. An agent that is already running never sees a note left afterwards (`relay note` says so). Notes are plain text: nothing checks that a later role honoured one, and a note cannot be retired or limited to one phase (a later note that says otherwise is the only way; agents are told a later note stands over an earlier one and that no note waives a required check). One note is limited to 4,000 characters, but the number of notes is not, and every later agent is given all of them. | A note left mid-phase takes effect from the next phase. Whether it was followed is for the Reviewer and the owner to see. | Open |
| `relay override` to an earlier phase is recorded as an approval. | The ledger reads as if the owner accepted work they were in fact rejecting. Use `relay send-back` where it is offered. | Open |
| A phase that was started and then stopped leaves a step with no artifact, and there is no way to mark it withdrawn. | The history shows a step that never produced anything. | Open |
| The Arbiter's judgment can be wrong. It decides a loop past the tripwire and every warning verdict, reading role reports and diffs that are attack surface, so a planted instruction could steer it to "move on". What fences it is code, not its judgment: a move-on stops for the owner while Security has reported a high since the latest Builder step or Relay's latest test run did not pass, and before it would close the task or reach Ops; a second re-plan on a task stops for the owner; a ruling Relay cannot act on exactly stops and never moves the task; an escalation's choices are only the owner's existing commands, and its gate carries the same warnings in Relay's words; where it offers a choice that closes the task or reaches Ops, which skips Security, it also warns when Security's latest report (its latest step with a verdict; an override past a report `relay next` has not read records its verdict) is a high with a Builder step after it, because Security has not run since that fix; while any of these Security warnings or a failed run stands, a choice that closes the task or reaches Ops is never the recommended one; where the passing run at the report it ruled on awaits the owner's confirmation (a changed test command, changed or unchecked harness files, fewer tests run) and a choice moves past that report, the gate gives Relay's reason, `relay next` and `relay gate-check` print the same harness lines as the approval gate, no such choice is the recommended one, and only taking such a choice after that records the owner's acceptance; at any Arbiter step, an override records no acceptance until `relay next` has recorded the ruling, so a report rewritten before then offers nothing; the card indents every continuation line of the Arbiter's reason and question, so none starts like Relay's own "Relay warns:" line; a targeted round counts toward the retry limit. The Arbiter's follow-ups and known flaws reach later roles as recorded by the Arbiter, not accepted by the owner, with no request not to raise them. A move-on at a Reviewer's or Tester's high on a risky task goes on to the next rating role, which judges the same commit: a move-on starts no Builder step. Confirmed by: the classes `TestTheBackstops` and `TestUnreadable` and `test_targeted_round_goes_to_the_builder_and_counts_as_an_automatic_round` (`orchestrator/tests/test_arbiter_routing.py`); the same commit by `test_security_after_a_move_on_past_a_tester_fail_closes_and_never_reruns_the_tester` there, whose history runs Tester, Arbiter, Security with no Builder step between; the escalation's warnings by the class `TestAnEscalationCarriesRelaysWarnings` there, and the handover by `test_security_is_never_told_to_keep_quiet_about_planted_arbiter_text` (`orchestrator/tests/test_arbiter_handover.py`). The unchecked fix by `test_a_close_after_an_unchecked_fix_of_a_security_high_warns_and_is_not_recommended` and `test_ops_after_an_unchecked_fix_of_a_security_high_warns_and_is_not_recommended`, and the indent by `test_the_arbiters_padded_reason_never_starts_a_card_line_as_relays_warning`, all in that class. The harness at an escalation by `test_a_close_past_an_unchecked_harness_names_it_and_is_not_recommended` and `test_a_choice_that_goes_back_carries_no_harness_warning` in that class, and `test_an_escalation_close_past_a_changed_harness_names_it_and_recommends_nothing`, `test_an_escalation_to_security_past_a_changed_harness_names_it_before_accepting` and `test_an_override_at_an_escalation_that_never_named_the_harness_accepts_nothing` (`orchestrator/tests/test_arbiter_real_runs.py`). The verdict an override records by `test_an_override_straight_after_a_security_high_still_warns_at_a_later_escalation` and `test_an_override_straight_after_a_security_high_still_stops_a_later_move_on`, and the recorded ruling by `test_an_override_before_relay_next_read_an_escalation_accepts_nothing` and `test_an_override_before_relay_next_read_a_move_on_accepts_nothing`, all in that file. An override made before Security has written its report records nothing, so a high written after that override still gives no warning (reasoned from the code, not run). | A wrong move-on at a Reviewer's or Tester's high, with Relay's run passing and no close or deploy ahead, is not stopped by Relay; the next rating role and the owner's later gates are what catch it. | Accepted limit |
| A medium does not stop for the owner, even under `--auto`, unless the Arbiter escalates. Every Reviewer `approved_with_warnings`, Tester `pass_with_concerns` and Security `findings` goes to the Arbiter, at any round, and its accept moves the task on. Confirmed by: `test_every_warning_verdict_runs_the_arbiter_at_round_zero`, `test_with_auto_the_arbiter_is_launched_by_its_role_name` and `test_accept_at_a_warning_gate_moves_on` (`orchestrator/tests/test_arbiter_routing.py`). | The owner reads a medium only where the Arbiter asks the owner, or at a gate a move-on stops at. What it accepted is in `relay status`, the card and the JSON API, and every later role is given it. | By design |
| What the count that calls the Arbiter counts: Builder steps that followed a Reviewer, Tester or Security report (an Arbiter step counts as the report it ruled on), whoever sent them back, since the latest Architect or Designer step after the first build (`arbiter.loop_counts`). A step after a failed Relay test run, after a re-plan, or an owner's override from any other step does not count. The count is 2 (`arbiter.REVIEW_LOOPS_BEFORE_THE_ARBITER`), a constant, not a setting. Confirmed by: `test_each_kind_of_builder_step_is_counted_or_not` and `test_the_count_starts_again_after_a_re_plan` (`orchestrator/tests/test_arbiter.py`). | A Builder step that ended `needs-architect` after a Reviewer's report counts as a review loop, so a re-plan reached that way counts one loop before it. Changing the number is a code change. | Accepted limit |
| Who started a review loop is read from the step before it: a high's own route is Relay's, a warning verdict's or an escalation's is the owner's, a targeted round is the Arbiter's. A send-back the owner makes at the retry limit's stop after a high reads as Relay's, because the step before it is the high. Confirmed by: reading `_builder_step` in `orchestrator/arbiter.py` (the branch for a rating phase gives `relay` for any verdict in `HIGH_VERDICTS`); the send-back case itself was not run. | A label in the breakdown by cause is wrong in that case; nothing that is counted changes. | Open |
| A missing Arbiter report reads as "waiting on the Arbiter" until `relay next` has looked. Relay cannot tell a running Arbiter from one that left nothing; the `arbiter_unreadable` gate is shown once `relay next` has found no readable decision and recorded that. A hung Arbiter is caught by the time limit and a crashed one by the non-zero-exit stop. Confirmed by: `test_a_missing_arbiter_report_stops_and_never_advances` (`orchestrator/tests/test_arbiter_routing.py`). | The card shows nothing to decide until `relay next` is run once more. | Accepted limit |
| A rolled-back install cannot save a task whose history holds an Arbiter step: the older code checks every step of a task's history against its phases on every save, and it does not know `arbiter`, so every save of that task is refused, an abort included. DEPLOYMENT.md says to close such tasks before rolling back. Confirmed by: reading `record_step_and_save` in `orchestrator/db.py` on the base branch (the check `if entry_phase not in _valid_phases`); not run against an older install. | Such a task is stuck under the older version until Relay is reinstalled. It fails closed: it does not route wrongly. | Open |
| For the move-on backstop, a latest test run that is `not_run` or `timed_out` counts as not passing. A task whose repo has no test command (Relay needs a profile, so rare) sends every move-on to the owner. Confirmed by: `test_a_latest_run_that_did_not_pass_includes_one_that_never_ran` (`orchestrator/tests/test_arbiter_routing.py`). | One extra stop per move-on, toward the owner. | Accepted limit |
| A warning verdict whose `relay next` was stopped after recording it and before the Arbiter was dispatched (a Ctrl-C during Relay's test run, say) reads afterwards as a warnings gate left standing from before the Arbiter: an approval gate that recommends a send-back, not a call to the Arbiter. Relay tells a gate left standing only by the verdict being recorded with nothing after it. A task standing at such a gate, or at a `fix_rounds` gate, when this version is installed reads the same way and keeps its choices. Confirmed by: `test_a_standing_warning_gate_stays_an_approval_gate` (`orchestrator/tests/test_arbiter_routing.py`), which builds exactly that state. | The owner decides that medium, as before the Arbiter; the task's next qualifying report goes to the Arbiter. | Accepted limit |
| A send-back with no note sets the count of automatic rounds back to 0 like any other. `relay send-back` prints that no note was recorded and how to add one. | A session can reset the count without saying why. The ledger shows that it was sent back and when. | Accepted limit |
| A task on the files backend has no events to recount, so a stored count of automatic rounds is kept as it is, including one counted under an older rule that also counted send-backs. | Such a task may stop at the limit one or more rounds early and ask. One `relay send-back` clears it. | Accepted limit |
| A `blocked` task reads as stopped at the limit only when its latest verdict is one Relay routes back on its own and the count for that phase is at the limit. Otherwise it reads "Paused" and does not take a send-back: for one, a stopped task after `max_retries` has been raised. Ledgers written by older versions of Relay can hold more such tasks. An override on a task that reads "Paused" resets only the count of the phase it moves to. | These move by `relay override <task> <phase>` or `relay abort`. Nothing in the ledger but the latest verdict and the count tells a stopped task from a paused one. | Open |
| A Builder's fix report is named `-fix-N` by the number of Builder steps before it in the task. An override into the Builder, and a Builder run after its own `needs-architect`, are therefore named `-fix-N` too. Reviewer and Tester reports take `-pass-N` from their own count of automatic rounds, which is almost always 0. | A file name says how many times the Builder ran, not why. The step number in front keeps names unique. | Accepted limit |
| Accepting Security findings and closing a task after a deploy both use `relay override <task> done` at the terminal. On the phone's card (`relay card`) they are two choices with their own names and words: `accept-close`, "Accept the findings and close the task. Nothing is deployed.", and `deploy-done`, "Close the task: you have deployed it and the smoke test passed." No card offers both, and its `move-to` leaves out `done` beside either. Confirmed by: `test_look_alike_choices_read_differently` and `test_every_gate_kind_has_its_choices` in `orchestrator/tests/test_gate_card.py`. | Typed at the terminal, only the gate kind tells the two apart. On the card the words do. | Open |
| Security's verdict is capped at `findings` whenever the repo's profile lists no `security_test_targets`, even for a documents-only task with nothing to attack. | Such a task always ends at an owner gate that recommends sending the work back, with no finding behind it. | Open |
| The prompt Relay prints for an agent carries only the task, its reading list (the brief, the latest report of each role that has run, the report the round answers, and every other file in the task folder as optional history), the paths, the recorded test run and, for the Reviewer, Tester and Security, one sentence naming the three ratings. Confirmed by: `test_rating_phase_is_told_the_three_ratings` and `test_other_phases_are_told_nothing_about_ratings` (`orchestrator/tests/test_phase_prompt.py`), which read what `agents.build_prompt` returns, and `test_required_lists_brief_designer_plan_and_latest_of_each_role_that_ran` (`orchestrator/tests/test_role_context.py`). | The owner's notes are added automatically. Whoever dispatches the agent still has to add by hand what kind of pass it is (a re-review, a re-test) and which commits changed. A dispatch without that context would repeat work or miss the owner's override of the brief. | Open |
| The legacy files backend records no events (approvals, send-backs, notes, test runs, sizing changes), and Relay runs no tests for a task on it. A new install is not on it: the example config an install copies sets `persistence_backend: sqlite`. Relay's own default is still `files`, so an install whose `config.yaml` names no backend, such as one copied from an older example, stays on it after `./setup.sh`. Confirmed by: `test_the_example_config_keeps_tasks_in_the_sqlite_ledger` and `test_an_install_whose_config_names_no_backend_stays_on_the_files_backend` (`orchestrator/tests/test_fresh_install.py`). | A task on that backend has no audit trail and no recorded test evidence. To move such an install, add `persistence_backend: sqlite` to its `config.yaml` (and run `relay recover --init` if there is no `relay.db`), then preview importing its tasks with `relay recover --from-projections` and import them with the same command plus `--apply` (DEPLOYMENT.md, "The backend, new and upgraded"). | Not planned; the files backend is legacy |
| The sizing hint reads only the names of the paths a branch changed, never their content: `risk_hint.work_out` lists them with `git diff --name-only` between the fork point (the merge base of the base commit Relay confirmed for the task and HEAD) and HEAD and matches the names against patterns. Input handling in a file named `utils.py` matches nothing. Confirmed by: reading `changed_paths` and `categorized` in `orchestrator/risk_hint.py` (no file is opened), and `test_a_diff_matching_nothing_says_so` (`orchestrator/tests/test_risk_hint.py`); the fork from the base commit by `test_the_sizing_hint_reads_the_fork_and_risk_paths_at_the_recorded_commit` (`orchestrator/tests/test_base_trust_twin.py`). | A risky change under a plain name gets no pointer. The Reviewer still reads the whole diff and may raise the sizing with no hint. | Accepted limit |
| The Reviewer's judgment can keep a risky diff at `risky: no`. A keep against a hint that matched needs only a one-line reason; Relay records it, shows it in `relay status`, the JSON API and the card at the task's next owner gate, and does not stop. A planted line in the diff could steer the Reviewer to keep. Confirmed by: `test_a_matching_hint_with_a_keep_routes_as_with_no_hint` (`orchestrator/tests/test_resize.py`), which shows routing identical to no hint and the keep on the card. | The Tester and Security are skipped on a task that needed them unless the owner reads the keep and re-sizes with `relay resize`. | By design |
| A Reviewer's or Arbiter's report can raise the sizing without cause: a raise with no reason still applies (recorded as "(the report gave no reason)"), and nothing checks that the work needed it. Confirmed by: `test_a_raise_without_a_reason_still_applies` (`orchestrator/tests/test_sizing.py`) and `test_a_reviewer_raise_to_risky_goes_to_the_tester_then_security` (`orchestrator/tests/test_resize.py`). | Extra roles run (cost only, never fewer checks). The owner can lower it with `relay resize`. | Accepted limit |
| On the files backend the sizing is the brief's plus the raises read back from the Reviewer's and Arbiter's reports (each report's first 64 KB); the hint is worked out and printed but not kept, so no answer is ever required, no keep or refusal is recorded, and `relay resize` is refused. Confirmed by: `test_the_files_backend_folds_raises_from_reports` (`orchestrator/tests/test_sizing.py`) and `test_resize_is_refused_on_the_files_backend` (`orchestrator/tests/test_resize.py`); that no answer is required rests on reading `risk_record.answer_required`, which needs a recorded hint, and `read_risk_hints`, which reads none on that backend, not on a run. The raises are read again from the reports at every read, so editing an earlier Reviewer's or Arbiter's report to take out its `sizing: raise` takes the raise away, and the Tester and Security drop out of the chain again. Confirmed by: a scratch script that called `sizing.read_sizing` on a files-backend task with a raise to risky in the Reviewer's report (it printed `risky = True`), then with the raise edited out of that report (`risky = False`); `_folded_judgments` in `orchestrator/sizing.py` reads every judging report each time. | A files-backend task never stops for an unanswered hint, and a raise there lasts only as long as the report that made it is unchanged. Use the SQLite ledger (the row above). | Not planned; the files backend is legacy |
| The default patterns match by name, so they make false matches: `*token*` matches a tokenizer, `*schema*` a JSON schema, `*migrat*` a module such as Relay's own `migrate_legacy.py`. Confirmed by: `risk_hint.matches("src/tokenizer.py", "*token*")` printed `True`, and matching every `orchestrator/*.py` name against the defaults found only `migrate_legacy.py` (schema). | On a `risky: no` task each such round costs one Reviewer answer (a keep with a reason), or a stop for the owner when it gives none. | Accepted limit |

## Ratings and the threat model

| Flaw | What it costs | Status |
| --- | --- | --- |
| Ratings by consequence and by the threat model are judged by the roles, not by code: whether a high names its wrong behaviour, its attacker or the decision that goes wrong, whether a finding is inside the threat model, and whether an untrue statement would lead to a wrong decision. No code reads either. The rules are under "Threat model and ratings" in `agents/builder.md`, `reviewer.md`, `tester.md` and `security.md`. | A role that rates by category is not stopped. The Reviewer and the owner are the check. | By design |
| Every role reads the repo's `.relay/threat-model.md` as it is at the task's base commit by its instructions (`git show <commit>:.relay/threat-model.md`, with the full commit id Relay confirmed for the base and names in the role's prompt). Relay's code does not read the file, and does not check that it exists, what shape it has, or that a role read the base's copy and not the branch's. Confirmed by: `grep -rn "threat-model" orchestrator --include=*.py --exclude-dir=tests` finds no line; `test_every_role_reads_the_threat_model_at_the_base` and `test_no_role_file_reads_the_threat_model_by_branch_name` (`test_agent_prompts.py`) hold the instruction, and `test_the_role_prompt_names_the_recorded_commit` (`test_base_trust_twin.py`) the commit in the prompt. | A role that reads the branch's copy, or none, works to the wrong model unseen until the Reviewer, Security or the owner reads its report. Security names a branch's change to the file as a finding. | Not built |

## Test evidence

| Flaw | What it costs | Status |
| --- | --- | --- |
| Relay does not check that a manual test plan exists when one is needed, that it was run, or that its results were filled in and committed. The Tester's prompt asks for the plan; nothing enforces it. Filling in results needs a text editor, not a phone. The plan's folder is fixed at `docs/manual-tests/`; a profile cannot move it. After the owner runs a plan and it passes, the gate still reads as a warnings verdict that recommends sending back; the owner accepts with `relay override`. | A task can be accepted at the gate with an unrun plan. The owner has to open the plan and see the empty "Actual" column. | Open |
| A task can complete without a passing recorded run at its final commit. | The rule "no pass or merge without a recorded passing run at that commit" is stated but not enforced. Security and Ops changes after the Tester are not re-tested by Relay. | Not built |
| Relay's recorded test run reports counts only. Nothing names the test files a round deleted, renamed or took a line out of. Confirmed by: the fields of `TestRun` (`orchestrator/evidence.py`) include `counts` and `seen_to_fail`, whose cases come only from test files the branch added or changed (`test_harness.changed_test_files` asks git for `--diff-filter=AM`), and no list of deleted or renamed files. | A rewritten test keeps the count, and only the Builder's list of existing tests changed or removed, and the Reviewer's own list from the diff, show it. | Open |
| Counts need a JUnit report named in the profile (`test_report`). | Repos that don't write one show "counts unknown". | By design |
| Harness files and test files are found by fixed rules, not by reading what the test command really runs. A harness file is one the base's command names, `package.json` or the `Makefile` for the tools that read them, common runner configuration by file name (for pytest: `conftest.py`, `pytest.ini`, `.pytest.ini`, `pytest.toml`, `.pytest.toml`, `tox.ini`, `setup.cfg`, `pyproject.toml`), the module a command runs with `python -m X` (`X.py` or `X/` in a folder the command runs from), a submodule the branch adds, removes or moves and `.gitmodules`, or what the `test_harness` list in the profile at the base commit Relay confirmed for the task names, each compared in any case (so a branch's `PYTEST.INI`, which pytest reads as `pytest.ini` on the Mac's disk, is harness); a test file is one under a `test`, `tests`, `__tests__`, `spec` or `specs` folder or with a test-like name. Any other branch code the run executes is neither, and can write its own report and exit 0. Confirmed by: `test_runner_config_and_profile_listed_paths_are_harness_but_tests_and_ci_are_not`, `test_every_configuration_file_pytest_reads_is_harness`, `test_a_module_that_shadows_the_runner_where_the_command_runs_it_is_harness` and `test_test_files_are_found_by_folder_or_name`; for any case, `test_harness_names_match_in_any_case` and `test_a_branch_that_adds_an_upper_case_pytest_ini_stops_for_the_owner`; and `test_a_branch_that_adds_a_dot_pytest_ini_loading_its_own_plugin_stops_for_the_owner`, where the plugin module that turns a failing test into a pass is not in `harness_changed`, only the `.pytest.ini` that loads it (all in `orchestrator/tests/test_evidence_harness.py`); for submodules, `test_a_branch_that_adds_a_submodule_has_changed_the_harness` and `test_moving_a_submodule_to_another_commit_is_a_harness_change_and_not_a_test_change`, and for the list read at the base commit, `test_a_branch_rebuilt_on_an_older_base_commit_still_gets_clean_mode_and_the_harness_list` (same file), and `test_a_branch_left_on_an_older_base_commit_keeps_the_rules_the_base_moved_to` (same file, through `relay next`). Also run that day: `python3 -m pytest` in a folder holding a `_pytest.py` ran that file instead of pytest, and the harness rule for Relay's own command (`cd orchestrator && python3 -m pytest ...`) answers no for `orchestrator/_pytest.py`. | A script that the named script calls, a helper module the tests import, a plugin loaded from a harness file, or a module the runner imports in turn (pytest's `_pytest`, `pluggy`, or a standard-library name placed in the folder `python -m` runs from) can change unseen unless the base profile lists it in `test_harness`, and can make a failing suite pass with the same count. A test file outside those folders and names is not run at the base. | Open |
| A harness file that is in the worktree but not in the commit still runs when clean mode is off, and the harness check never sees it: that check reads only the commit's changes against the base, while the run executes the worktree. Two ways: a tracked file (a `conftest.py`, say) flagged skip-worktree or assume-unchanged with `git update-index` and then edited, which `git status` does not show, so the run is not `uncommitted` and nothing notes it (`uncommitted_changes` in `orchestrator/evidence.py` asks only `git status --porcelain`); or a file under a folder the branch's own `.gitignore` hides, which leaves only the note "Ran with ignored files present: ...". Confirmed by: two scratch set-ups, one for each way: each recorded a failing pytest suite as `passed`, with `harness_changed` empty and no stop for the owner. With `test_clean_checkout: true` in the base's profile, the same two set-ups recorded `failed`, "Ran in a clean checkout" (two scratch tests run that day, not committed). | A Builder or Tester that writes the worktree can make a failing suite pass in Relay's recorded run with nothing in the branch's diff; a role that reruns the tests in a clean clone would still see the failure. `test_clean_checkout: true` in the base's profile is the mitigation: the run then uses a fresh checkout of the commit, which holds neither file. Relay's own profile does not turn it on yet. | Open |
| The default harness list includes files that also hold other things: `pyproject.toml`, `setup.cfg`, and `package.json` when the command runs npm, npx, yarn or pnpm. Confirmed by: the same test asserts `pyproject.toml` is harness. | A branch that only changes a dependency in one of them stops for the owner once for that change. | Open |
| Seen to fail matches a test case to a changed file only by the JUnit report's `file` attribute or the leading words of its `classname`. A case that errors at the base, or whose whole file failed to load there (pytest reports that as one error case with no classname, named after the module), is "could not check". When no test at the base passed, failed or was skipped, every case missing from its report is "could not check" as well ("the run at the base stopped before any test ran": pytest runs no test once one file fails to load). Otherwise a case missing from the base's report is "did not run", not "failed". Confirmed by: `test_unmatched_cases_give_could_not_check`, `test_an_import_error_at_base_is_could_not_check_not_failed` and `test_a_skip_at_base_or_a_missing_case_did_not_run`, `test_a_file_that_could_not_load_at_base_is_could_not_check`, `test_a_missing_case_did_not_run_when_other_tests_ran_at_base` and `test_a_base_run_stopped_by_a_test_file_that_cannot_load_could_check_nothing` (all in `orchestrator/tests/test_seen_to_fail.py`). That a run stopped after some tests ran gives "did not run" for the rest is read from `seen_to_fail._at_base`, not run. | Runners whose reports name neither give "could not check" for every new test.
